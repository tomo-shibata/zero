# TDD スキル

テスト駆動開発（Test-Driven Development）で機能追加・バグ修正を実装するためのスキル。

## 使うタイミング

- ユーザーが **「TDD」「テスト駆動」「Red・Green・Refactor」** を明示的に指定したときにだけ使う。
- それ以外のときは、このスキルを自動的に適用しない。

## 事前に読むこと

- `docs/rules/test/architecture.md`（テストルール。特に「仕様からテストを作る」「実装から独立」「mockのトートロジー回避」「実行のたびにDB作成」を厳守）
- 対象パスに一致するアーキテクチャルール。

## 進め方

### 0. テストリストを作る

- まず **仕様（仕様書）** から、実装すべき振る舞いを **テストリスト**（箇条書き）に起こす。
- 実装コードからテストを起こさない（トートロジーテストを避けるため）。

### 1件ずつ、以下のサイクルを回す

テストリストの項目を **一件ずつ** 取り、次を繰り返す:

1. **Red** — 失敗するテストを1つ書く。実行して「期待どおり失敗する」ことを確認する（コンパイルエラーではなくアサーション失敗で落ちるのが理想）。
2. **Green（最小）** — テストを通すための **最小限の実装** を書く。きれいさは後回しで、まず通す。
3. **Refactor** — テストが緑のまま、重複除去・命名改善・責務分割などで整える。各ルール（SRP等）に沿わせる。

- 1サイクルごとにテストを実行し、緑であることを確認してから次の項目へ進む。
- テストリストが尽きるまで繰り返す。途中で気づいた新しいケースはテストリストに追記する。

## 注意

- テストは実装とは独立に、仕様ベースで書く。
- mock を多用した「呼んだことを確認するだけ」のトートロジーテストを避ける。
- UI や実行時の挙動に関わる場合、静的なテスト／レビューだけに頼らず、最後は実際に動かして確認する。
