# セルフレビュー スキル

プルリクエストを出す前に、**作成者自身**で変更を点検するためのスキル。
Google の [Engineering Practices](https://google.github.io/eng-practices/)（CL author's guide と Code Reviewer's Guide）を参考にしている。

## 使うタイミング

- PR を作成する前、レビューを依頼する前（`pull-request` スキルや AI相互レビューの前段）。

## 事前に

- `git diff`（または対象ブランチとの差分）で、**自分が変更した全行を自分で読む**。
- 対象パスに一致するルール（`docs/rules/**`）を読み、違反がないか確認する。

## セルフレビューのチェック観点

Google の「What to look for in a code review」に沿って、自分の変更を次の観点で点検する。

### 1. 設計（Design）
- 変更はシステムに対して筋が良いか。置き場所（レイヤー・ディレクトリ）は適切か。
- 既存のものと統合されているか。今入れるべき変更か。

### 2. 機能（Functionality）
- 作者の意図どおり動くか。その意図はユーザーにとって妥当か。
- エッジケース・並行処理・異常系を考慮したか。

### 3. 複雑さ（Complexity）
- 必要以上に複雑になっていないか。「今は不要な将来向けの作り込み（過剰な一般化）」をしていないか。
- 読んだ人がすぐ理解できるか。

### 4. テスト（Tests）
- 変更に対応する適切なテストがあるか（`docs/rules/test/architecture.md` に準拠：仕様ベース・実装から独立・トートロジー回避）。
- テストは正しく、意味のある失敗をするか。

### 5. 命名（Naming）
- 変数・関数・型の名前は、それが何であり何をするかを十分に伝えているか。

### 6. コメント（Comments）
- コメントは「なぜ（why）」を説明しているか（「何を」はコードで表現）。
- 不要になったコードはコメントアウトで残さず削除したか。

### 7. スタイル / 一貫性（Style / Consistency）
- プロジェクトのスタイル・既存コードの流儀に合っているか。
- リンタ・フォーマッタを通したか。

### 8. ドキュメント（Documentation）
- 必要なドキュメント（`docs/` の SSOT、OKF形式）を更新したか。

### 9. 全行（Every Line）
- 差分の **すべての行** に目を通したか。コンテキスト（周辺コード）も踏まえて妥当か。

### 10. 良い点
- うまく書けている箇所も把握しておく（PR本文やレビューで共有できる）。

## CL（変更）の大きさと説明

- **小さく保つ**: 1つのPRは1つの自己完結した変更に絞る。大きければ分割を検討する。
- **説明を整える**: `pull-request` スキルの本文構成（課題・背景・解決策・テスト・レビュー観点）に沿って、レビュアーが上から読めば理解できるようにする。

## 仕上げ

- UI や実行時の挙動を変えた場合、静的な点検だけでなく **実際に動かして確認** する。
- 指摘が自分で見つかったら、レビュー依頼前に直す。直さない項目は PR本文の「未対応事項」に書く。
